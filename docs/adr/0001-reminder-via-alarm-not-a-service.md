# 提醒用系统闹钟承担，不做常驻服务，也不因「应用被关掉」而取消

起因是用户提的要求「我想要提醒，但不要定时提醒」。追问之后真实目标是**省电**：「关掉应用就不再提醒」只是它的一条代理要求。
于是决定：一次提醒 = **一个一次性的系统闹钟**（有精确闹钟权限时用精确闹钟，否则回退不精确闹钟），**不引入前台服务、不加常驻通知、不在应用被划掉时取消已排的提醒**。代价是提醒可能晚几分钟、手机重启会丢闹钟；收益是空闲时**零耗电**、应用可以随时被系统冻结或杀死而不影响提醒送达。

## 考虑过并放弃的方案

- **前台服务 + 常驻通知**：可靠、可见、划掉即停；但要让进程和一条通知陪用户数小时，与「省电」这一真实目标直接冲突。另外 `shortService` 类型上限约 3 分钟（官方原文），盖不住 30 分钟的间隔，只能用 `specialUse`。
- **"应用被关掉就不再提醒"**：实现它必须跑一个服务去接 `onTaskRemoved`，为检测「被关掉」而常驻的耗电**多于**它想省的那点电。所以不实现，并把这个代理要求明确作废。
- **按用户在其它应用里的活动来提醒**（使用情况访问 / 无障碍服务）：隐私与上架合规代价远大于一个打卡应用的价值，且国产 ROM 上不可靠。
- **每天固定时刻的提醒**：用户最初明确不要。后来接受的是**开始提醒** —— 只在「当天还没有任何勾选」时才发，且锚在活动时间开始，不是无条件的每日闹钟。
- **`USE_EXACT_ALARM`**（安装即授予、免用户操作）：官方政策只允许核心功能是闹钟/计时器/日历的应用声明它；本项目不是，不写不实的声明。
- **顺延机制**（到期落在活动时间之外就顺延到次日窗口开始）：一旦有了「开始提醒」，顺延就没有存在意义了，规则简化为一句「提醒只在活动时间内工作」。

## 后果

- 没有精确闹钟权限时，提醒**可能晚几分钟**（官方文档没有给出延迟上界，代码里也不假装有）。
- 手机在提醒前重启 → 闹钟消失，只会在下次打开应用时由界面上的「已超时」说明兜底。
- 应用权限从 0 条变为 2 条（`POST_NOTIFICATIONS`、`SCHEDULE_EXACT_ALARM`），README 里原先「零权限」的说法必须改写。
- 在活动时间之外勾选一组**不会**排提醒 —— 规则只有一条：提醒只在活动时间内工作。
